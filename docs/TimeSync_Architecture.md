# TimeSync Database Guide (Zero-Trust Security Architecture)

This guide documents the complete Supabase architecture for the TimeSync feature. Because the app uses VTOP local login instead of Supabase Auth, we have implemented a **Zero-Trust Device Secret** architecture to guarantee mathematically that no one can spoof requests or steal timetables.

## 1. Tables

### `users` Table
Stores the student's profile, their locally synced timetable, and their TimeSync credentials.

**Columns:**
- `reg_no` (text, Primary Key): The student's registration number (Max 12 chars).
- `name` (text): The student's full name.
- `timetable_json` (jsonb): The JSON representation of their weekly timetable.
- `unique_pin` (text): The 6-digit numeric PIN given to friends to request access.
- `device_secret` (uuid): **[NEW]** A hidden, highly secure UUID generated by the app. This acts as the user's secret password to prove their identity to the database.
- `fcm_token` (text, nullable): The Firebase Cloud Messaging token for push notifications.
- `last_synced` (timestamp): The last time they opened the app and synced their timetable.

### `friendships` Table
Stores the relationships between users.

**Columns:**
- `id` (uuid, Primary Key): Auto-generated unique identifier.
- `user_a_id` (text, Foreign Key to `users.reg_no`): The person who SENT the request.
- `user_b_id` (text, Foreign Key to `users.reg_no`): The person who RECEIVED the request.
- `status` (text): Can be `'pending'`, `'accepted'`, or `'rejected'`.
- `created_at` (timestamp): When the request was initiated.

## 2. Row Level Security (RLS) & Strict Lockdown

> [!CAUTION]
> To ensure zero-trust security, we will completely block the `anon` (anonymous) role from directly querying or modifying ANY tables. The tables will be 100% invisible to the public. 

**Run this SQL in Supabase to lock down the tables:**

```sql
-- 1. Add the device_secret column to the users table
ALTER TABLE users ADD COLUMN IF NOT EXISTS device_secret UUID;

-- 2. Drop any existing public policies you might have added earlier
DROP POLICY IF EXISTS "Allow public read users" ON users;
DROP POLICY IF EXISTS "Allow public insert users" ON users;
DROP POLICY IF EXISTS "Allow public update users" ON users;
DROP POLICY IF EXISTS "Allow public read friendships" ON friendships;
DROP POLICY IF EXISTS "Allow public insert friendships" ON friendships;
DROP POLICY IF EXISTS "Allow public update friendships" ON friendships;
DROP POLICY IF EXISTS "Allow public delete friendships" ON friendships;

-- 3. Ensure RLS is enabled on both tables
ALTER TABLE users ENABLE ROW LEVEL SECURITY;
ALTER TABLE friendships ENABLE ROW LEVEL SECURITY;

-- 4. Create explicit "DENY ALL" policies just to be absolutely sure (optional, as default is deny, but good for visibility)
CREATE POLICY "Deny All users" ON users FOR ALL USING (false);
CREATE POLICY "Deny All friendships" ON friendships FOR ALL USING (false);
```

Since the tables are completely locked down, the *only* way the app can read or write data is by calling the **Secure RPC Functions** below, which run as an admin (`SECURITY DEFINER`) and verify the `device_secret`.

## 3. Secure Remote Procedure Calls (RPCs)

These functions bypass RLS because they use `SECURITY DEFINER`. They explicitly check the `device_secret` before allowing any data to be read or written.

**Run this massive SQL block in Supabase to create the secure backend:**

```sql
-- ============================================================================
-- 1. OPT IN & SYNC
-- Upserts a user's data. If the user already exists, it verifies their secret first.
-- ============================================================================
CREATE OR REPLACE FUNCTION opt_in_user(
  p_reg_no text, 
  p_name text, 
  p_timetable jsonb, 
  p_pin text, 
  p_secret uuid, 
  p_time text
) RETURNS void AS $$
DECLARE
  existing_secret uuid;
BEGIN
  SELECT device_secret INTO existing_secret FROM users WHERE reg_no = p_reg_no;
  
  IF existing_secret IS NULL THEN
    -- New user, insert them
    INSERT INTO users (reg_no, name, timetable_json, unique_pin, device_secret, last_synced)
    VALUES (p_reg_no, p_name, p_timetable, p_pin, p_secret, p_time::timestamp);
  ELSIF existing_secret = p_secret THEN
    -- Existing user, verify secret, then update
    UPDATE users SET 
      name = p_name, 
      timetable_json = p_timetable, 
      unique_pin = p_pin, 
      last_synced = p_time::timestamp
    WHERE reg_no = p_reg_no;
  ELSE
    RAISE EXCEPTION 'Unauthorized: Incorrect Device Secret.';
  END IF;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- ============================================================================
-- 2. UPDATE FCM TOKEN
-- ============================================================================
CREATE OR REPLACE FUNCTION update_fcm_token(p_reg_no text, p_secret uuid, p_token text) 
RETURNS void AS $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM users WHERE reg_no = p_reg_no AND device_secret = p_secret) THEN
    RAISE EXCEPTION 'Unauthorized: Incorrect Device Secret.';
  END IF;
  
  UPDATE users SET fcm_token = p_token WHERE reg_no = p_reg_no;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- ============================================================================
-- 3. REGENERATE PIN
-- ============================================================================
CREATE OR REPLACE FUNCTION regenerate_pin(p_reg_no text, p_secret uuid, p_new_pin text) 
RETURNS void AS $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM users WHERE reg_no = p_reg_no AND device_secret = p_secret) THEN
    RAISE EXCEPTION 'Unauthorized: Incorrect Device Secret.';
  END IF;
  
  UPDATE users SET unique_pin = p_new_pin WHERE reg_no = p_reg_no;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- ============================================================================
-- 4. SEND FRIEND REQUEST
-- Verifies sender secret, checks rate limit, verifies target PIN, inserts request, resets target PIN.
-- ============================================================================
CREATE OR REPLACE FUNCTION send_friend_request(p_sender_reg text, p_sender_secret uuid, p_target_reg text, p_target_pin text) 
RETURNS void AS $$
DECLARE
  v_recent_attempts int;
BEGIN
  -- 1. Verify Sender Secret
  IF NOT EXISTS (SELECT 1 FROM users WHERE reg_no = p_sender_reg AND device_secret = p_sender_secret) THEN
    RAISE EXCEPTION 'Unauthorized: Incorrect Device Secret.';
  END IF;

  -- 2. Verify Target PIN exists and is correct
  IF NOT EXISTS (SELECT 1 FROM users WHERE reg_no = p_target_reg AND unique_pin = p_target_pin) THEN
    RAISE EXCEPTION 'Incorrect PIN or user does not exist.';
  END IF;

  -- 3. Insert friendship (Rate limiting trigger will fire here automatically if you set it up previously)
  INSERT INTO friendships (user_a_id, user_b_id, status) VALUES (p_sender_reg, p_target_reg, 'pending');

  -- 4. Burn the target's PIN so it can't be used again
  UPDATE users SET unique_pin = floor(random() * (999999-100000+1) + 100000)::int::text WHERE reg_no = p_target_reg;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- ============================================================================
-- 5. ACCEPT FRIEND REQUEST
-- ============================================================================
CREATE OR REPLACE FUNCTION accept_friend_request(p_target_reg text, p_target_secret uuid, p_sender_reg text) 
RETURNS void AS $$
BEGIN
  -- Verify Target Secret
  IF NOT EXISTS (SELECT 1 FROM users WHERE reg_no = p_target_reg AND device_secret = p_target_secret) THEN
    RAISE EXCEPTION 'Unauthorized: Incorrect Device Secret.';
  END IF;

  UPDATE friendships SET status = 'accepted' 
  WHERE user_a_id = p_sender_reg AND user_b_id = p_target_reg;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- ============================================================================
-- 6. CANCEL / REMOVE FRIEND
-- ============================================================================
CREATE OR REPLACE FUNCTION remove_friend(p_my_reg text, p_my_secret uuid, p_other_reg text) 
RETURNS void AS $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM users WHERE reg_no = p_my_reg AND device_secret = p_my_secret) THEN
    RAISE EXCEPTION 'Unauthorized: Incorrect Device Secret.';
  END IF;

  DELETE FROM friendships 
  WHERE (user_a_id = p_my_reg AND user_b_id = p_other_reg) 
     OR (user_b_id = p_my_reg AND user_a_id = p_other_reg);
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- ============================================================================
-- 7. READ SECURE DATA (Friends list and Pending lists)
-- These verify the secret before returning any data.
-- ============================================================================
CREATE OR REPLACE FUNCTION get_my_friends(p_my_reg text, p_my_secret uuid)
RETURNS TABLE (reg_no text, name text, timetable_json jsonb) AS $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM users WHERE users.reg_no = p_my_reg AND users.device_secret = p_my_secret) THEN
    RAISE EXCEPTION 'Unauthorized: Incorrect Device Secret.';
  END IF;

  RETURN QUERY
  SELECT u.reg_no, u.name, u.timetable_json
  FROM users u
  JOIN friendships f ON 
    (f.user_a_id = p_my_reg AND f.user_b_id = u.reg_no) OR 
    (f.user_b_id = p_my_reg AND f.user_a_id = u.reg_no)
  WHERE f.status = 'accepted';
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE OR REPLACE FUNCTION get_pending_incoming(p_my_reg text, p_my_secret uuid)
RETURNS TABLE ( reg_no text, name text ) AS $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM users WHERE users.reg_no = p_my_reg AND users.device_secret = p_my_secret) THEN
    RAISE EXCEPTION 'Unauthorized: Incorrect Device Secret.';
  END IF;

  RETURN QUERY
  SELECT u.reg_no, u.name
  FROM users u
  JOIN friendships f ON f.user_a_id = u.reg_no
  WHERE f.user_b_id = p_my_reg AND f.status = 'pending';
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE OR REPLACE FUNCTION get_pending_outgoing(p_my_reg text, p_my_secret uuid)
RETURNS TABLE ( reg_no text, name text ) AS $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM users WHERE users.reg_no = p_my_reg AND users.device_secret = p_my_secret) THEN
    RAISE EXCEPTION 'Unauthorized: Incorrect Device Secret.';
  END IF;

  RETURN QUERY
  SELECT u.reg_no, u.name
  FROM users u
  JOIN friendships f ON f.user_b_id = u.reg_no
  WHERE f.user_a_id = p_my_reg AND f.status = 'pending';
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

## 4. Supabase Edge Functions

### `friend-request-notification`
This is a TypeScript Edge Function hosted on Supabase.
- **Trigger:** It is triggered by a Database Webhook whenever an `INSERT` or `UPDATE` happens on the `friendships` table.
- **Routing:** It includes a data payload `{"route": "/connect"}` so the Flutter app knows to open the Connect tab when the notification is tapped.
